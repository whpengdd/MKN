## Context

隐墨是纯 Markdown 编辑器,核心信条:**小体积**(刚由 Electron 351MB 迁到 Tauri ~5.6MB DMG)与**本地 .md 字节级零损失往返**。当前 `open_file_dialog`(`src-tauri/src/files.rs:32`)仅放行文本扩展名,且用 `read_to_string` 读取 —— 选中 `.docx`(本质是 zip)会直接报错/崩。用户需求经探索澄清为最窄一档:**只导入查看、丢样式、不回写**。

关键既有抽象:`src/shell/doc.ts` 中 `path = null` 即「未命名草稿」,自动保存**仅在「有 path 且 dirty」时落盘**(doc.ts:136),草稿绝不自动写盘 —— 这恰好就是「导入只看、不破坏原文件」需要的安全边界,无需新建只读模式。

## Goals / Non-Goals

**Goals:**
- 用户能选中并查看 `.docx` 内容,以 Markdown 形式呈现于编辑器。
- 导入对原 `.docx` 零副作用(永不回写)。
- 体积增量控制在 +1~2MB 二进制内,DMG 仍保持个位数 MB。
- 前端改动最小化,复用既有「未命名草稿」机制。

**Non-Goals:**
- 不打包 pandoc;不追求样式/高保真。
- 不做 `.docx` 回写、往返编辑。
- 不支持旧版 `.doc` 二进制格式。
- 不保留图片/公式/批注/修订。

## Decisions

**D1:转换放 Rust 侧,用 `docx-rs`。**
- 理由:与现有 open/save 架构同一条线,前端几乎零改动;`docx-rs` 提供结构化文档树,映射子集比手解 OOXML XML 稳。体积 +1~2MB 在预算内。
- 备选:① `zip`+`quick-xml` 手解(体积更小 ~+0.5MB,但要自己处理样式/列表/表格的 XML 细节,工期与缺陷风险更高);② JS `mammoth.js`(成熟,但隐墨是 markdown 编辑器,需再 HTML→markdown 一道,且要把库接进 open 流程,前端改动反而更大)。选 D1 是工期/稳定/架构一致性的平衡。

**D2:`open_file_dialog` 内按扩展名分支,而非新增独立命令。**
- 理由:对前端透明 —— 返回结构不变(`{ path, content }`),`.docx` 时令 `path = null`、`content` 为转换后的 markdown。前端无需感知来源。
- 备选:新增 `import_docx` 命令并在前端分流 —— 前端要改打开逻辑,违背「前端最小改动」目标。

**D3:`.docx` 分支强制 `path = null`(未命名草稿)。**
- 理由:复用 doc.ts 既有「草稿不自动保存」行为,天然满足「不回写原文件」需求,无需引入新只读状态机。

**D4:转换失败返回 `Err(String)`,不 panic。**
- 理由:`read_to_string` 当前会让命令对二进制文件报错;统一为可读错误,前端已有 notify 错误通道。

## Risks / Trade-offs

- **语义损耗用户感知**:复杂排版 Word 导入后「变样」→ 用户可能觉得工具搞坏文件。**缓解**:仅作未命名草稿、绝不回写原 `.docx`;必要时在导入后给一次性提示「已按纯文本导入,样式已丢弃」。
- **`docx-rs` 解析覆盖面/维护度**:某些 Word 生成器的 XML 变体可能解析不全。**缓解**:目标只是「能看」,解析不到的结构降级为纯文本/丢弃而非报错;非法文件返回明确错误。
- **体积超预算**:`docx-rs` 拉入较多依赖致二进制 >2MB。**缓解**:实现后量测 release 二进制增量,若超标回退到 D1 备选①(`zip`+`quick-xml` 手解)。
- **`.doc` 误选**:用户选了老 `.doc`(扩展名相近)。**缓解**:解析失败返回「不支持旧版 .doc」类错误,不崩。
